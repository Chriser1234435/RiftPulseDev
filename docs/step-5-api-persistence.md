# Step 5 — API contracts and persistence

Status: **Complete for the local contract/schema foundation.** The authenticated claim operation remains deliberately gated until Step 6 supplies the verified website session.

## V1 boundaries

The shared contract package is the source of truth for the V1 API vocabulary:
- Modules: `chat`, `bsr-song-request`.
- Providers: Twitch, YouTube, Kick, TikTok (TikTok remains explicitly unofficial/best effort).
- Targets: PCVR and standalone Quest.
- Pairing code is generated by the mod and is exactly five digits; it is not generated or returned by the website/API.

## Current routes

- `GET /api/v1/health` — service and API version.
- `GET /api/v1/version` — V1 modules and API version.
- `POST /api/v1/pairing/challenges` — validates a mod-generated code, stores an HMAC-SHA-256 digest, and returns a random challenge ID and expiry without echoing the code.
- `GET /api/v1/pairing/challenges/:id` — reports the challenge status.
- `POST /api/v1/pairing/claim` — validates the request shape and returns 401 until website authentication is implemented. It does not bind a device to a caller-provided account ID.

Pairing challenges expire after five minutes. A device can have at most three active challenges. Expired code digests are cleared so they can no longer be claimed. The five-digit space is small, so this is not sufficient by itself for a production pairing flow: before launch, add authenticated website claiming, robust per-IP/device rate limiting, attempt throttling, collision retries, and security review. Never log raw codes or include them in error telemetry.

## Schema

Migration `0001_initial.sql` creates accounts, devices, pairing challenges, provider connections, module settings, chat commands, song requests, provider health, and idempotency keys. It includes foreign keys, enum checks, unique constraints, indexes, and bounded command cooldowns.

Provider access and refresh token columns are placeholders for ciphertext only. The future integration layer must encrypt tokens using a managed secret/key design; never store plaintext tokens or place credentials in source control.

## Local development

Use only local commands during Step 5:
- `npm run db:migrate:local`
- `npm run db:migrations:local`
- `npm test`

The Wrangler D1 binding uses a placeholder UUID and does not identify a real remote database. Do not use `--remote`, create a Cloudflare database, or deploy during this step.

Cloudflare documents D1 local development as a standalone local environment; applying migrations with `--local` targets local state rather than remote D1. See https://developers.cloudflare.com/d1/best-practices/local-development/ and https://developers.cloudflare.com/d1/reference/migrations/.
