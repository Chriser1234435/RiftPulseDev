# RiftPulseDev — V1 Architecture Proposal

**Status:** Step 3 design draft. This is documentation only; no application code, cloud resources, credentials, DNS, or deployments have been created.

## 1. V1 scope

Only two modules ship in V1:

1. **Chat:** aggregate supported livestream chats into a floating in-game chatbox, show an aggregated viewer count with a person icon, and support configurable chat commands.
2. **BSR Song Request:** accept chat requests, validate BeatSaver song keys, apply queue/cooldown rules, and deliver the queue to the game.

Targets are Beat Saber PCVR and standalone Quest. Share API contracts and business rules, but keep separate game-specific adapters and build/test pipelines. The website configures account, platform connections, pairing, module settings, commands, and the request queue.

## 2. Proposed technology architecture

- **Repository:** new monorepo in `Chriser1234435/RiftPulseDev`; do not import source, migrations, secrets, or deployment configuration from previous attempts.
- **Website + API:** TypeScript/React SPA with Vite, served with the API by one Cloudflare Worker using Static Assets. Cloudflare recommends Workers Static Assets for new full-stack projects: https://developers.cloudflare.com/workers/static-assets/
- **Database:** Cloudflare D1 for account/auth tables, devices, pairing state, platform connection metadata, module settings, and song-request queue.
- **Realtime:** Cloudflare Durable Objects coordinate WebSocket sessions and event fan-out. Cloudflare recommends Durable Objects when multiple WebSocket connections need shared coordination: https://developers.cloudflare.com/workers/runtime-apis/websockets/
- **Authentication:** evaluate Better Auth with D1; Clerk is explicitly excluded. Validate current Workers/D1 compatibility and email-delivery requirements before implementation: https://better-auth.com/docs
- **No Neon, Railway, R2, separate API host, or Pages project is required by this initial design.** R2 is out of scope unless a demonstrated V1 need appears.
- Keep development and production resources, credentials, and databases separate.

## 3. Logical components

### Website
Polished, animated dashboard with module cards, provider connection health, device pairing, command/settings configuration, and the BSR queue. Show clear connecting, connected, disconnected, and degraded states.

### Edge API
Same-origin `/api/v1/*` endpoints for authentication callbacks, account/device authorization, pairing, settings, provider status, and queue operations. Use schema validation, restrictive CORS, CSRF protection for cookie-authenticated mutations, request IDs, and rate limits.

### Persistence and realtime
D1 stores durable configuration and queue records. Durable Objects coordinate live device sessions and send normalized events to paired PCVR/Quest clients. Do not persist full chat history by default.

### Shared contracts
Version and validate `ChatMessage`, `ViewerCountSnapshot`, `ProviderHealth`, `PairingStatus`, `DeviceSession`, `SongRequest`, `ModuleSettings`, and `ApiVersion`. Device telemetry includes platform, gameVersion, modVersion, and apiVersion.

### Game adapters
- **PCVR:** C# Unity/Beat Saber mod using a verified compatible loader/UI library. Installed game is 1.40.8, but target framework and loader references must be verified before pinning build settings.
- **Quest:** separate Android/Quest standalone build and compatibility layer. Android SDK/ADB and Quest build tools were not detected; verify/install them in the authorized toolchain step.
- Never assume a PCVR DLL runs on Quest. Both clients consume the same API contracts and expose equivalent module states.

## 4. Streaming provider adapters

Each platform adapter has its own connection lifecycle, health state, normalized chat events, and viewer-count snapshot support. Provider failures must not take down other integrations. Encrypt OAuth tokens at rest; keep encryption keys in Worker secrets, never in source or browser bundles.

- **Twitch:** official OAuth and EventSub/chat APIs where supported. https://dev.twitch.tv/docs/chat
- **YouTube:** official Live Streaming API; prefer `streamList` where appropriate to receive updates efficiently. https://developers.google.com/youtube/data/live/reference/rest/v3/liveChatMessages/streamList
- **Kick:** isolated adapter; validate current developer API access, OAuth scopes, and chat capabilities during implementation rather than assuming permissions.
- **TikTok LIVE:** user accepts an unofficial username-based connector. Isolate it behind a replaceable adapter, label it unofficial/best-effort, and report unsupported/disconnected/degraded status honestly. Prove its runtime feasibility before selecting deployment location.

## 5. Pairing flow — code generated by the mod

1. User selects **Connect to website** in the RiftPulse game tab.
2. Mod uses a cryptographically secure random generator to create a five-digit code and registers it with the API over HTTPS.
3. API stores a keyed digest, installation challenge, expiry, and attempt count; reject active-code collisions and rate-limit registration.
4. Mod displays the code; user signs in to the website and enters it.
5. API validates the authenticated account, expiry, and attempt limits, then atomically consumes the code and binds the device.
6. Mod shows loading, a success checkmark, animated “Welcome to RiftPulse”, then the module menu.
7. Website can revoke a device; device credentials can be rotated.

Proposed expiry is five minutes. Five digits have limited entropy, so codes are one-time, short-lived, account-gated, rate-limited, stored as keyed digests, and never treated as long-term credentials. Never authorize a device based only on a client-supplied account ID. Do not log raw codes or device secrets.

## 6. Chat and viewer-count flow

Provider adapter → validation/deduplication → normalized event → command dispatcher → in-game chatbox and/or BSR handler → authenticated device event stream.

Normalize provider, channel, user display name, text, provider message ID, timestamp, and event type. Bound message length, escape rendered text, deduplicate reconnect replay, and enforce command cooldowns. Only configured commands may trigger actions.

Viewer count is a sum of fresh, valid provider snapshots—not the number of chatters. Never silently treat unavailable counts as zero. If a provider count is missing/stale, display a partial/degraded indicator beside the known total.

## 7. BSR Song Request flow

Proposed default command: `!bsr <BeatSaver-key>`, configurable by the streamer. Parse safely, validate the key against supported BeatSaver metadata/API, enforce duplicate and per-user cooldowns, apply queue settings, and enqueue a normalized request. The website displays queue state. The game adapter handles platform-specific loading and confirms success; do not mark a song loaded before confirmation. Show unavailable songs and load failures explicitly.

## 8. Proposed API surface

- `GET /api/v1/health` — service/version health.
- `POST /api/v1/pairings` — register a mod-generated code.
- `POST /api/v1/pairings/claim` — authenticated one-time claim.
- `POST /api/v1/devices/renew`; `DELETE /api/v1/devices/:id` — renew/revoke.
- `GET/PATCH /api/v1/settings/modules` — module configuration.
- `GET/POST/DELETE /api/v1/integrations/:provider` — connect/disconnect.
- `GET /api/v1/integrations/status` — provider health and count availability.
- `GET/POST/PATCH/DELETE /api/v1/song-requests` — queue operations with authorization.
- `GET /api/v1/devices/:id/events` — authenticated WebSocket upgrade routed to a Durable Object.

Names are provisional until locked by contract tests.

## 9. Logical data model

- Auth/session tables managed by the chosen first-party auth library.
- `devices`: owner, platform, game/mod/API versions, created/last-seen/revoked timestamps, credential digest/status.
- `pairings`: keyed code digest, installation challenge, expiry, attempt count, consumed timestamp.
- `provider_connections`: owner, provider, external account ID, encrypted tokens, scopes, expiry, status, last error code.
- `module_settings`: owner, module key, validated settings, revision.
- `song_requests`: owner, requester identity, provider, song key/metadata, queue position/status, timestamps, failure reason.
- `security_events`: minimal security metadata; never raw OAuth tokens or pairing codes.

## 10. Security and reliability

- No secrets in Git, browser bundles, screenshots, or logs. Commit placeholder-only `.env.example` files.
- Encrypt platform tokens at rest; store encryption keys in Worker secrets and plan rotation.
- Use Secure/HttpOnly/SameSite session cookies, CSRF protection, OAuth state validation, and exact redirect URI validation.
- Enforce pairing expiry, one-time use, rate limits, request-size limits, input validation, provider backoff, retry budgets, and deduplication.
- Keep provider health independent and explicit.
- Preserve all existing email/domain DNS records. A development hostname can be connected only in a later authorized step; final tests must use the real development hostname, not only a preview.
- No provider is complete until consent, refresh, disconnect/revocation, and live-event behavior are tested.

## 11. Visual design

The in-game UI should be a polished Beat Saber mod menu inspired by the user's BS+ reference: compact readable cards, clear icons, restrained accent lighting, consistent spacing, and responsive feedback. RiftPulse appears alongside other mods. The main page includes pairing, module cards with status/toggle/configure actions, top-right settings gear, and top-left back action. Toggles save automatically. Website animations must remain usable with reduced-motion preferences.

## 12. Test and release gates

1. Unit/contract tests: pairing expiry/replay/rate limits, authorization, event normalization/deduplication, viewer aggregation, command parsing, and queue invariants.
2. API integration tests: D1 migrations, auth sessions, OAuth callback validation, device revocation, WebSocket reconnect/delivery.
3. Provider tests: mocks for rate limits, revoked tokens, missing viewer counts, reconnects, and TikTok degradation.
4. PCVR build and smoke test against a pinned Beat Saber/loader combination.
5. Quest build and actual-headset smoke test, including pairing and chat display.
6. End-to-end test on the actual Cloudflare development hostname.
7. Release only after both targets and both V1 modules pass acceptance tests.

## 13. Risks to validate before implementation

- Pin PCVR mod loader/UI library and target framework for Beat Saber 1.40.8.
- Verify Quest loader, Android SDK/ADB, native build prerequisites, and supported game version.
- Verify platform app registration, OAuth scopes, refresh rules, developer access, and viewer-count availability.
- Prove TikTok connector compatibility/runtime feasibility. If it cannot run reliably in Workers, present a separate hosting decision before adding another service.
- Choose a transactional email provider if the auth configuration needs verification/reset email.
- Prove Better Auth + Workers + D1 compatibility in a minimal test before locking dependencies.
- Do not configure credentials, create cloud resources, or deploy until the design is approved and the next step is authorized.

## 14. Explicit V1 exclusions

No modules beyond Chat and BSR Song Request; no imported legacy code; no Clerk; no DNS/cloud mutation during Step 3; no production resources; no claim that TikTok is official; no claim that unavailable viewer counts are zero.
